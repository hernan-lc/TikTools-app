# Aggregation work in progress

The Rust host owns ranking accounting. Accepted native LIVE deltas are applied before presentation events are published. Consumers can request `rankings.snapshot` and subscribe to the `ranking.updated` domain topic. Updates are coalesced and may be dropped; control clients should request a fresh snapshot after connecting or detecting a gap. The widget-scoped gateway allows `ranking.updated` and receives periodic refreshes every five seconds for read-only reconnection. `instanceId` identifies a ranking instance and is retained on clean checkpoint recovery; `revision` identifies changes within that instance. Legacy snapshots and checkpoints may omit the identity.

Presentation events carry at most the first 100 entries, matching the widget's rendering limit; totals still include all participants. To stay within transport limits, unusually large snapshots omit optional identity and artwork, then reduce the visible prefix if needed. The control snapshot uses the configured Top N, and winner selection uses the complete bounded ranking.

The desktop WebView coalesces pending ranking snapshots by ranking ID and keeps lifecycle events on its reliable lane. Like snapshots are also replaceable; clients recover the latest snapshot after a gap or reconnect.

`TIKTOOLS_RANKING_PUBLISH_INTERVAL_MS` controls the background polling interval in milliseconds (default 250, clamped to 50–1000). This interval also controls competition deadline polling. Top candidates are selected from a shared ordered index and ranked outside the ingestion lock; no snapshots are assembled while no domain subscriber exists.

`system.health.aggregations` reports the number of rankings, paused and degraded rankings, and aggregate rejected, dropped, limited, and cooldown-rejected counts. Degraded rankings also affect the overall health status. These counters describe local state and do not establish upstream completeness.

Definitions support session and bounded rolling windows. A rolling window expires each contribution at its acceptance timestamp plus `durationMs`. `maxEvents` limits retained contributions; rejecting an event degrades the snapshot. Ordinary rankings, including their bounded rolling and per-user-limit state, are checkpointed on drained shutdown and consumed once on startup; an interrupted run can lose changes and causes affected rankings to be marked degraded on recovery. Dedicated competition vote rankings are reconstructed from durable participant assignments. Integrity is `unknown` unless a local accounting failure makes it `degraded`; it is not a claim that upstream delivery was complete.

Competition work is incomplete. Polls, team battles, option roulette, and participant draws using the durable option ranking can finalize manually or on their deadline. Leaderboard challenges are not yet supported. Winner actions for selected options are dispatched from a durable outbox through the existing automation runtime; participant draws do not execute an option action.

The standalone `/widgets/ranking/` bundle accepts `rankingId` and `visualization` query parameters. Visualization may be `ranking`, `bar`, `pie`, `donut`, or `poll`; the chart percentages use the full snapshot total, with omitted entries grouped as Other. `widgets.copyObsUrl` accepts `widget: "ranking"`, `rankingId`, and an optional `visualization` and places the scoped credential in the fragment. The renderer displays at most 100 entries, shows local integrity and pause states, and rejects scores that JavaScript cannot represent exactly. The existing alert editor does not yet configure this widget.

The Likes widget uses a bounded native `live.likes-ranking-full` snapshot of up to 500 entries, including for configurations above ten rows. Its per-user scores and ordering use the shared bounded aggregation primitive; the legacy `live.likes-ranking` topic still provides its top-ten projection. This leaderboard is distinct from loyalty points and TikTok room-provided viewers. Ties are ordered by stable user identity. The compatibility projection is still separate from user-defined ranking instances and their snapshot topic.

An in-memory synthetic throughput baseline is available with `cargo run --release -p tiktools-aggregation --example throughput`. It does not measure SQLite, upstream loss, memory, or winner finalization.

Competition command definitions are indexed by creator, room, and normalized whole command. The index is rebuilt from stored definitions at startup and rejects ambiguous routes and capacity overflow. Matching accepted native chat commands are processed in ingress order and recorded transactionally, independently of presentation and effects streams. `system.health` exposes `competitionParticipation` counters. A dedicated session ranking grouped by option with a `competition.vote` / `event.count` rule projects committed command votes, including switches, and is rebuilt from participant assignments and committed routed scores on restart. Only one competition may reference such a ranking. Reset the ranking before reusing it for a new competition. Like and share deltas may also contribute after the viewer selects an option. Contributions remain with the option selected at the time of each event; switching moves command votes but does not move prior scored contributions. Gift combo contributions require a stable sender, gift and group identity and a known nonzero price; ambiguous gifts or a combo first observed after its initial packet degrade the ranking instead of being guessed. A directly mapped gift counts its sender once toward minimum participation without selecting an option for subsequent likes or shares; a later command from the same sender does not count them twice. A command and its projection are serialized with lifecycle transitions; commands still waiting in the ingress queue can be overtaken by a control operation. Recognized commands ignored while paused, after a deadline, or because of a vote limit or forbidden switch retain their event identities within the same bounded generation ledger. Replaying them after a later state change cannot create a vote; if the ledger is full, participation fails closed and diagnostics report the failure.

`rankings.metrics` (or `tiktools ranking metrics`) lists the native metrics implemented so far and their packet or delta meaning. A source rule may include `giftMultipliers`, an object mapping gift IDs to nonnegative integer multipliers; absent IDs use 1 and 0 disables that gift for the rule. Each score is `delta × weight × gift multiplier`, summed with checked integer arithmetic. Weights and multipliers are limited to 1,000,000,000, and each rule can hold at most 512 gift overrides. Overflow rejects the contribution for that ranking. No rounding occurs. A gift without an ID is rejected for a rule with gift overrides rather than guessing an override.

If a gift streak's price appears late and would retroactively revalue previously unpriced gifts, the diamond metric is rejected and affected rankings are marked degraded. A final packet with no new quantity does not contribute a gift event or diamond score.

The loyalty points leaderboard remains a separate balance projection. Its decimal balances, manual adjustments, and queued LIVE awards are not yet an authoritative `points.awarded` aggregation source; competition scores do not change loyalty balances. TikTok room-provided top viewers retain their own provenance in the feed.

Optional `userLimits` accepts `maxContributions`, `cooldownMs`, and required `maxUsers` (1–100,000). At least one positive limit or cooldown is required. A contribution is one accepted, nonzero scored packet, regardless of its quantity or grouping; limits apply across all groups for that user and last until reset, including when rolling-window scores expire. Cooldown uses host acceptance time and clock regressions are clamped. Policy exclusions increment snapshot `limited` or `cooldownRejected` without degrading integrity. Missing user identity, exhausted user capacity, and arithmetic errors reject accounting and degrade integrity. Limit state is currently in memory and is lost on restart along with ranking scores.

Committed winner history can be read with `competitions.results` or `tiktools competition results <id>`. The RPC accepts an optional `limit` (1–20, default 10) and exclusive `beforeGeneration` cursor; `nextBeforeGeneration` is returned when another page exists. Results are retrieved from durable records and reading them never repeats a draw or action. Unsupported types and unresolved ties stay in `finalizing`.

`competitions.action` reads the public outbox status and a sanitized failure reason for a competition generation without returning action inputs, raw error text, or idempotency keys. The last reason is retained after manual resolution as diagnostic history. The privileged `competitions.resolveAction` records `completed` or `failed` only when the existing state is `uncertain`; it never requeues or executes the action. CLI equivalents accept `--record` JSON, for example `tiktools competition action --record '{"id":"poll","generation":1}'` and `tiktools competition resolve-action --record '{"id":"poll","generation":1,"resolution":"completed"}'`. The bounded worker executes pending actions through the existing automation runtime. An execution error or interrupted invocation becomes `uncertain` and is not retried. A host crash may leave an action `running`; after verifying the executor is no longer running, an operator can use privileged `competitions.markActionUncertain` or `tiktools competition mark-action-uncertain --record '{"id":"poll","generation":1}'` before resolving it. Automatic startup recovery is not connected.

With `allowSwitch`, a user may select a different option even after reaching `voteLimit`; at the limit this changes the assignment without adding a vote. Switching before the limit adds one vote. The stored participant retains the total count with the latest option; command identities remain recorded for replay protection. The dedicated command-vote ranking projects these assignments.

`competitions.finish` and `tiktools competition finish <id>` close and select a winner for polls, team battles, option roulette, and participant draws that use a dedicated `competition.vote` ranking. Option contests use the complete bounded ranking rather than its display limit; participant draws use the durable participant ledger. Selection and any winner action outbox are stored transactionally before the result is returned. A degraded ranking, insufficient participation, empty candidates, or a manual tie remains in `finalizing`; winner actions run through the existing automation executor after the result is committed.

Competition start, pause, resume, cancel, finish, winner selection, and action outcome events are available to domain subscribers and the automation runtime with typed context. Winner and action outcome events follow their database commits, and retrying a finished result does not emit another winner event. Domain and automation delivery are bounded and are not a durable event outbox: a crash between commit and publication or a saturated automation queue can lose a notification. Recover state through the result and action APIs; reloading does not replay effects.

Active command-vote competitions use a conservative integrity checkpoint. A cleanly drained shutdown records whether the ranking was degraded; an unclean restart or missing checkpoint marks it degraded and prevents winner selection. This does not prove upstream delivery was complete. Shutdown waits up to five seconds for the checkpoint. A per-host ownership token fences delayed checkpoints, votes, lifecycle changes, and result writes from an older host after recovery begins. Cancelled or abandoned ingress prevents a clean checkpoint.

Ranking snapshots include optional source-provided display identity and artwork, with a stable key fallback for the label. Metadata is bounded by ranking capacity, changes only alongside accepted scoring, and is evicted when an entry expires. The widget accepts HTTP(S) artwork without embedded credentials. Command-vote option labels are reconstructed from stored competition definitions.

The desktop navigation includes Rankings & competitions. It creates and previews session or rolling rankings, edits paused ranking definitions, copies ranking OBS URLs, and creates and operates competitions with existing automation actions. Scoring or scope changes require an explicit reset. Workflow references and the full visualization editor are not yet implemented in this page.

For a manual highest-score tie, `competitions.candidates` returns the tied leaders from the full closed ranking. `competitions.selectWinner` accepts the competition ID, generation, and one tied winner ID; the decision is stored once before its action is dispatched. The management page offers the same choice.

Ranking OBS URLs support `showLabels`, `showPercentages`, and `showLegend` boolean query parameters. Pie and donut charts show scores outside the displayed entries as an “Other” slice based on the snapshot total.

Team battles using an option-grouped competition ranking treat each configured option as a team. Commands select a team, and committed likes and shares add to the selected team under the same switching and replay rules as polls.

The read-only `competition.result` topic periodically republishes a presentation projection of the latest committed result for each finished competition while clients are subscribed. It includes at most 256 candidates, always retaining the stored winner, plus the total eligible count and the omitted candidates' aggregate weight. The full eligible set remains in the persisted result accessible through the control API. Publication never exposes an in-progress selection or executes actions.

The ranking widget also accepts `visualization=roulette`, which animates toward the winner in the stored `competition.result`. It does not select or dispatch actions. Repeated snapshots do not restart the animation; reconnecting can replay the same committed reveal.

The competition management panel can copy a winner reveal URL scoped to both its competition ID and ranking ID. The host validates that the competition references the ranking before copying it.

Result snapshot refresh errors are logged independently of the deadline and finalization pass; a presentation read failure does not prevent other competitions from finalizing.

A `random_draw` using a durable option ranking and `uniform_random` selection draws among distinct committed participants, including gift-only entrants. The eligible identities and winner are stored before publication; repeated finalization returns that result. Participant winners are not interpreted as option IDs or dispatched to option winner actions. `weighted_draw` uses each participant’s committed command vote score plus their accepted routed scores as ticket weight, with checked integer arithmetic.
